## 1. 服务数据契约

按实际来源与板块逐项明确以下内容，维护于已有板块方案，不为本策划复制完整字段目录。

| 审查项 | 需要形成的结论 |
| --- | --- |
| 输入 | 上游表、来源版本、数据层及已确认范围；直接使用raw/cleaned的例外引用当前授权契约 |
| 对象与粒度 | 一行是什么：基因、条目、isoform、序列、注释陈述、药理靶点或结构观察 |
| 主键与link | 项目归属、原始对象、关系含义、多对多情况、身份/序列/坐标关联层次 |
| 字段 | 类型、单位、是否可空、用于查询/关联/证据/追溯的理由 |
| 状态 | 来源缺失、解析失败、规则排除、未映射和不适用的区分 |
| 精简 | 明确重复且可恢复的字段是否通过实体表或视图取得；不能因同值就合并不同语义 |
| 更新依赖 | 上游或规则改变时需重建的表、视图和下游关系 |

蛋白条目是检索入口，不等于所有注释的实际对象。基因背景不能分配为全部isoform的注释；未限定isoform的条目注释不改写为canonical特异；明确isoform注释即使尚无序列也保留；位置型注释必须绑定具体序列或结构。来源具名对象未解析不等于条目通用。

关系link与网页URL分开设计：前者保存对象及科学语义；后者是导航。固定外链可通过实体字段与受控规则/视图得到；特殊来源地址及追溯信息按需保留。当前已实施的精简以[交付记录](../../../../record/00_initial_preview/20260921_basic_info_v2.md)为准，其他候选研究不自动变为删除授权。

## 2. 构建和入库

契约确认后，在相应授权内完成：指定快照输入 → 服务Parquet → 受影响关系核对 → PostgreSQL临时schema导入 → 视图与实际查询验证 → 事务发布。

继续使用现有入口和配置，具体步骤见[本地构建](../local_table_build.md)与[数据库方案](../postgresql.md)。构建、导入、查询验证应对应同一data_version和built_at；文件存在、脚本存在或历史文字不能代替实际成功记录。

这一阶段可使用代表性SQL检验查询可用性，不要求先确定前端折叠、图标、布局和每个可见字段。已确认数据范围内的构建照常推进，未确定的科学选择只阻塞依赖它的步骤。

## 3. 展示数据、形式与API契约

相关板块数据契约已稳定，初版依据PostgreSQL实际字段和用户“基本信息从简、来源细节展开、按类别筛选”的要求完成数据取舍，再落实具体交互形式和API契约。后续继续按同一顺序审查调整；需要用户判断时说明建议与取舍。已有板块内容范围及科学规则继续有效，不以页面方便为由新增科学处理。

| 契约 | 决定什么 | 例子 |
| --- | --- | --- |
| 数据库存储 | 服务查询、关联、完整已选注释及回溯所需字段 | 多条证据、isoform适用对象、原/目标坐标和状态 |
| API返回 | 每类请求需要的字段、筛选条件、分页及详情结构 | 列表不携带全部长文本；详情仍可读取所选证据 |
| 前端展示 | 用户当前任务需要看见的信息、记录范围与布局 | 只展示部分字段或按明确条件截选记录 |

展示截选不要求删除服务库内容，更不删除上游科研事实。普通分页、字段选择、来源/对象筛选可在Web层落实；新的收录规则、代表项、排名、阈值、跨来源合并或统计语义仍需回到负责模块确认。摘要须保留适用对象、单位、证据性质等影响解释的限定信息。

接口按研究任务组织，并与选定展示内容对照；不要求数据库表与前端组件一一对应。布局可先做必要的轻量原型，但静态原型不能替代真实数据链路。

数据库优化随实际查询推进，沿用[架构方案](architecture.md)的边界：先明确查询字段、过滤、排序和分页，再检查SQL计划与接口负载；针对瓶颈调整查询和索引，只有昂贵且科学口径已确认的汇总才考虑预计算。现有导入与SQL验收不替代API或并发验证，也不要求在展示审查前再次全库扫描或重构。

## 4. 按板块完成完整链路并迭代

整体次序为：公共身份/状态/API基础 → 相关板块真实查询与前端 → 跨板块联动与一致性验证。当前初版已完成这些步骤的本期实现和本地联调；后续板块或调整继续按实际依赖推进，无需等所有远期模块完成。

蛋白身份、isoform、功能和定位已构成真实链路。验收继续选有条目注释、isoform特异注释、HPA基因背景及缺失/未解析情况的真实样例，以验证对象层次，不能只选信息齐全的样例。

功能通路、序列/膜、结构、变异、PPI、QTL、Expression与疾病已接入本地初版，具体范围与限制见交付记录。已有[序列计划](../sequence.md)等科学边界仍由原文维护，本目录不另建竞争顺序。数据总览依赖已确认指标和实际可查询数据；不能提前用原始行数代替实体数量。

## 5. 必要验收

- 同一对象从不同入口查询，ID、来源和数据版本一致。
- isoform与序列位置配对正确；选择变化后旧请求不得覆盖新对象结果。
- 条目通用、明确isoform、基因背景和未解析对象可区分；不为填满页面强配。
- 未映射结构记录保留原对象和状态，但不定位到候选或相邻残基。
- 筛选、计数与下载采用相同口径；小数/频率单位正确，NULL不补零。
- 已确认范围的数据在接近实际规模上检查分页、响应及资源使用；小样例通过不能证明全站并发能力。
- 重建或入库失败不覆盖当前可用服务数据；运行结果和已交付状态及时更新到原有入口。

本策划维护方法，实际实现与验收结果维护于[初版方案](../website_v1.md)及[交付记录](../../../../record/00_initial_preview/20260921_website_v1.md)。当前同一8000端口、单FastAPI进程提供静态前端与API，复用现有PostgreSQL；没有执行公网上线、TLS配置或并发压测，本地验收不替代这些工作。
