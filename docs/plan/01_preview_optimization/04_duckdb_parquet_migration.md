# 04 DuckDB＋Parquet 后端减容与迁移计划

更新：2026-10-01。**迁移、API／网页验收与现有预览服务切换已完成。** 本轮以数据储存和处理为优先，保持前端信息展示；原 PostgreSQL、旧服务数据及大型原生资源保留，等待用户审查网页。此前“仅交付计划”的范围由本轮实施授权替代。

本方案替代旧方案中“全部 Web 服务表必须导入 PostgreSQL”的技术要求，以及存储讨论中优先保留 PostgreSQL 或优化 AlphaGenome 的建议。现有科研规则、收录范围、数据含义及网站展示契约继续适用；科研模块的 raw、cleaned、curated 不因本次 Web 迁移改变。

## 当前情况与目标

当前网站由 React／TypeScript 前端、FastAPI API 与 PostgreSQL 服务数据库组成。AlphaGenome 参考轨道为外部原生 HDF5，当前由 PostgreSQL 提供目录和关联，再按区间读取文件；结构文件也有独立资源依赖。

2026-09-30 19:32:23 北京时间只读核对：PostgreSQL 约 **200.44 GB**，业务 schema 共 156 张物理表、44 个普通视图、233 个索引、118 个登记外键。变异来源详情与 QTL／表达是主要容量对象。已有三处服务 Parquet 合计约 22.610 GB，但尚未证明涵盖数据库全部内容，不能据此承诺迁移后的大小。证据统一见[存储审查](../../research/01_preview_optimization/alphagenome_storage.md#2026-09-30数据库减容审查建议尚未实施)。

目标是降低网站后端数据的持久存储和未来部署包占用，以 **DuckDB＋Parquet** 完成迁移。减容依靠存储组织、无损压缩和查询实现调整，最终可将数据与前后端代码部署到云端。

**第一原则：迁移后前端的功能、使用模式、交互、信息量和科学含义保持不变，相当于仅进行后端压缩与重构。** 当前数据库保留但未在前端展示的记录和字段同样完整保留。

## 已确认边界

- **完整保留数据。** 以迁移时明确版本的当前 PostgreSQL 逻辑内容为基线，包括隐藏字段、来源详情、JSON／数组内容、映射状态、库内生成的关系和查询所需派生内容。复用已有 Parquet 前确认其与基线逐表对应，不直接回退到原始来源或重新筛选数据。
- **完整保留 link 与关联。** 蛋白—gene—序列—site，以及变异、评分、ddG、疾病、来源证据等已有关联，保持原 ID、版本、粒度、连接条件和一对多／多对多语义。没有直接 link 的对象不强行增加关联；已有未匹配或不可获取状态不丢弃。基因关联不能替代蛋白／isoform 精确序列匹配。
- **保持原值和解释。** 不通过删列、删记录、降采样、降低精度或改阈值减容；保留真实零与缺失、负值、坐标体系、来源单位、分类和代表项选择。类型可作无损映射，必须核对范围、精度与 API 返回类型。
- **原 PostgreSQL 暂时保持不动。** 迁移只读旧库，新产物和候选配置独立构建；不改旧表、视图、索引、角色、权限、存储目录或凭据，不调用会修改旧库的初始化／导入流程，不清理旧库文件。完成前后端适配及检查后，再由用户决定是否删除之前的数据；验证通过不构成自动删除授权。
- **AlphaGenome 大型数据暂不优化。** 原生 HDF5／预测资源的内容、dtype、chunk、压缩及窗口组织保持原状，不重压缩、不转 Parquet、不重算。现有 PostgreSQL 中的 AlphaGenome 目录、评分、AVI 与关联仍属于结构化服务数据迁移范围；读取和展示行为保持一致，不留下必须依赖旧 PostgreSQL 的运行链路。
- **本轮实施迁移。** 用户授权逐表分析、完整一致快照导出、存储构建、API 适配和前后端验收；普通技术取舍自主解决。新发现且会改变科学含义或范围的问题，只暂停依赖该决定的步骤。云端上传和删除旧数据不在本轮范围。

## 目标架构与逐表决策

FastAPI 使用 DuckDB 查询 Parquet 外部表／视图及必要的 DuckDB 原生表，向现有前端提供等价 API。AlphaGenome 和结构等外部资源继续按当前契约提供。

本计划**不预先指定任何具体表的存储位置**，也不规定所有关系表都入库或所有大表都外置。后续 agent 根据体积、粒度、实际查询与关联、分页／排序、更新方式及完整部署包大小决定：

| 待分析事项 | 决策要求 |
| --- | --- |
| 哪些表直接保存为 Parquet | 保留完整内容，确定支撑实际查询的分区、排序、文件和 row group 布局 |
| 哪些表存入 DuckDB 内部 | 说明原生表、统计、约束或索引的实际作用，计入额外存储成本 |
| 哪些逻辑通过视图／JOIN 表达 | 与原查询结果和关系语义一致，不为合表放大一对多数据或丢失来源 |
| 是否需要查询投影或派生索引表 | 明确与完整内容的对应关系和重建方法，避免无收益的全量重复保存 |
| 如何维护跨文件关系 | 构建／发布时核对关联键与引用一致性；不宣称数据库外键自动约束外部 Parquet |
| 如何部署与更新 | 明确一致快照中的文件组合、可重定位配置，并验证实际进程模型与并发查询 |

落定后在本方案维护逐表决策入口，实际表／视图定义与文件映射以构建代码及简明清单为准，不另建重复目录。具体布局、压缩参数、原生索引和连接管理交由后续 agent 分析；容量收益须实测，不预设压缩比例或固定最终 GB。

### 实施入口与实际依赖

逐对象决定以候选 `manifest.json` 的 `storage`、`columns`、`files`、`order_by` 和布局记录为准，构建代码为 [migrate_duckdb.py](../../../src/database/migrate_duckdb.py)，位置集中在 [duckdb.yaml](../../../config/duckdb.yaml)。全库以当前 PostgreSQL 导出，不直接复用旧服务 Parquet，避免遗漏库内新增关系或字段。当前初始方案为 156 张物理表完整 Parquet、40 个逻辑视图、4 个特殊 JSON 视图物化；实际查询布局与容量维护于[存储实施记录](../../record/01_preview_optimization/duckdb_storage_migration.md)。未通过完整验收的候选不作为已发布数据。

| 页面／查询流程 | API 入口与结构化依赖 | 独立资源 |
| --- | --- | --- |
| 首页统计、蛋白搜索及概览 | `catalog_statistics`、`core` 与概览汇总；`web` 身份、功能、定位、膜分类及原 build manifests | 同快照 `catalog_statistics.json` |
| 膜、Sequence Viewer 与位点证据 | `sequence`、膜与界面 API；`web` 序列／PTM／膜／保守性、`web_interface` 预测与关系 | 无新增科学输入 |
| Structure Viewer 与残基选择 | `structures`；当前 `web.protein`／`protein_sequence` 精确序列核对 | 原结构 `manifest.parquet` 与 PDB 文件，根目录可配置 |
| Variant Catalog、来源详情、频率与预测 | 变异查询／summary／support；`web_variant` 全部字段与关系、`web_variant_sequence` 精确序列、`web_clinvar_snv` 条件证据 | 完整来源 JSON 已包含在迁移范围 |
| Expression、Protein abundance、PPI 与 QTL | context／PaxDB API；`web_context` 与 `web_paxdb` 测量、长数组、数据集与关联 | 完整已导入测量内容，无运行时科研模块回读 |
| 疾病分类与来源证据 | disease／classification／PTMD API；`web_disease`、`web_classification`、ClinVar 与 PTM 关联 | 无新疾病归类或映射 |
| AlphaGenome、AVI 与 MANE CDS 共轴 | AlphaGenome／AVI API；`web_alphagenome` 目录、`web_avi` 归因、`web_mane` 模型及当前变异 | 原生 HDF5，版本校验及可配置资源根目录 |

Python 查询层使用显式的 PostgreSQL→DuckDB AST 适配，保持 JSON、数组、原列标签、NULL、float4 返回表达、原 libc 文本排序和 QTL `ctid` tie-break。原前端源码与构建保持，完整快照和网站验收通过后已切换 8000，原 ngrok 隧道与地址保留。真实来源记录按 footer locator 定位文件，不重复保存 JSON；查询实现与性能证据见实施记录。

## 执行顺序与阶段交付

### 1. 固定基线并盘点依赖

只读盘点物理表、视图、字段、主外键、已有关系、API SQL、服务构建脚本及外部资源。绑定明确的数据库内容版本、代码版本与上游输入，导出时保证一致的逻辑快照，不混入迁移期间的新旧版本。

交付表与关系清单、已有 Parquet 对应情况，以及页面—API—表／资源依赖。追查来源 JSON、库内新建关系、直接从科研模块导入的表和 AlphaGenome 目录；不能仅以 `Web/data/tables/` 作为完整迁移范围。先读元数据与必要样本，不无故反复扫描全库。

### 2. 分析存储方式并验证候选查询

由后续 agent 逐表决定 Parquet、原生 DuckDB、视图和必要查询结构。使用真实数据验证蛋白检索、序列／位点关联、变异筛选和来源详情、QTL 分页等代表查询，再针对实际规模确认响应、内存、临时磁盘与并发行为。

交付逐表存储决定、依据、影响及必要实测。关系表可能有大量记录，不能按名称推定体积；原生表更快或 Parquet 更省空间均须在实际查询中判断。局部原型不覆盖正式服务产物。

### 3. 实现可重建的数据迁移

在 Web 内提供统一构建／迁移入口，配置维护来源、目标位置和资源根目录；从完整基线读取旧库或复用已确认等价的 Parquet。生成候选 Parquet、DuckDB 和表／文件映射，保存输入版本、字段契约、行数和关联键等必要信息。

先写临时位置，检查后发布一致快照；失败不得覆盖可用产物。原 PostgreSQL 与上游数据保持原位。新旧数据共存会增加本机占用，须预估目标数据、临时空间与构建成本；分别报告新后端大小和共存阶段占用。

### 4. 完成 API 与前端适配

适配查询和连接管理，处理 PostgreSQL 特有 SQL、JSON／数组、NULL、类型及序列化差异。保留原筛选、搜索、分页、排序、计数、详情、下载和资源读取；分页不能因引擎变化而跳项或重复。

完成前端重构所需的接入调整，保持现有页面、交互模式、显示字段、科学配色与信息量，不附带界面改版。无须修改的部分保持原实现。候选服务使用独立配置对照，不替换旧库或改写原数据库配置。

### 5. 检查数据、关联与页面等价性

证明全量逻辑内容保留，不能只以若干页面能打开或抽样行数相同验收。按表和字段结构检查行数、键、类型、完整值及必要汇总／差异，结合迁移过程核对完整性；JSON／数组按原逻辑语义比较，不能因文本顺序变化误判或忽略内容缺失。

核对记录覆盖与关系基数，保留基线已有孤立／未匹配状态，不为“零孤立”补关联或删记录。对照受影响 API 的结果、类型、筛选、计数、分页与不可用状态；浏览器验证所有主要板块的关键流程和代表边界，包括序列／结构位点、来源详情、QTL、疾病与 AlphaGenome 轨道。

完成直接相关构建和回归检查，记录覆盖范围与限制。性能按真实使用流程及实际规模判断，发现明显退化先修复；不新增复杂 QC，不计算 SHA-256，不在已通过后无故重复全量扫描。

### 6. 交付可独立部署的新后端

交付构建入口、数据／资源清单、配置、启动方法及验证摘要，确认运行时不再需要原 PostgreSQL，也不依赖开发机器固定绝对路径。未来部署包包含代码、必要 Parquet、DuckDB 和外部资源；凭据独立配置，数据不随源码提交 GitHub。

报告新结构化后端总容量、查询表现、仍保留的 PostgreSQL 与未优化的 AlphaGenome 容量；部署数据和仅用于重建／历史核查的文件分别说明。云端位置与文件盘／对象存储方式在部署任务落实，本计划不自动授权上传。检查完成后提交清理旧数据的依据供用户决策，**原 PostgreSQL 在决定之前继续保留不动**。

## 完成标准与当前状态

迁移完成须同时满足：

1. 当前数据库全部记录、字段、来源详情和已有关系在新结构中可追溯、可查询，隐藏信息完整保留。
2. 网站使用 DuckDB＋Parquet 独立运行，所有主要板块的前端功能、模式、信息量和科学含义与基线一致。
3. 实际规模的关键查询与并发验证通过，记录容量收益、资源需求和未解决限制，不以小样本成功代替全量可用。
4. AlphaGenome 大型资源保持原状且相关页面可用，原 PostgreSQL 未被修改或删除。
5. 构建、启动、更新和未来部署配置可复用，检查结果及后续清理决定入口明确。

当前状态：200 个逻辑对象的结构化存储构建与核验已完成，156 张物理表共 519,366,173 行，4 个物化视图和 40 个等价逻辑视图完整保留。当前完整运行包约 27.33 GB，数据／布局证据以[实施记录](../../record/01_preview_optimization/duckdb_storage_migration.md)和机器清单为准。摘要及变异关联查询的执行退化已修复，不改变来源标签、原值或关系语义。

数据迁移、API 适配、独立等价验收由三名 GPT6.1 sol subagent 分工完成，主 agent 协调架构、启动配置、资源可重定位与交付。524 个真实 API 案例全部通过严格对照，相关回归测试和桌面关键流程通过。完整数据规模下默认 20 条列表首访约 0.8 s、摘要约 1.7 s，26 请求／4 并发 warm 最大响应约 0.95 s；仍比已预热 PG 慢，缓存、平台与负载限制详见记录。
