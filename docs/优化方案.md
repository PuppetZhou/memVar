# memVar 网站技术架构评审与优化方案

> 审查快照：2026-08-23  
> 审查对象：<code>/home/xuyzh/memVar/website</code> 及其声明的只读上游数据  
> 代表性页面：EGFR / UniProt P00533，桌面与窄屏实机浏览  
> 目标：为 SCI 配套数据库形成可发表、可检索、可引用、可维护的展示与工程方案

## 0. 结论摘要

memVar 的数据组织基础是扎实的：规范 UniProt accession 作为页面身份、上游只读、离线生成查询资产、QTL/Interaction/Disease 保留来源语义、128 桶确定性分区，以及 DuckDB 摘要与 Parquet 明细分离。这些设计比“把所有来源拼成一个总分”更符合科研数据库的可审计性要求。

目前的主要短板不在“数据层次不清”，而在展示和交付：

1. **科研入口不完整。** 首页仍显示 “Current scope · M3”，与实际已包含 Structure、Disease、AlphaGenome、Stability、Anatomy 等能力不符；缺少 Browse、Download、API、版本、引用和示例入口。
2. **蛋白详情页像模块堆叠，而非研究路径。** 十个平级导航项、无当前章节指示，窄屏后半段入口隐藏在横向滚动中；首屏之后几乎所有区段同时挂载取数。
3. **位点证据没有形成纵向结论栈。** 选中 residue 后的预览主要显示变异；JSD、Stability ΔΔG、covalent bond 仍散落在横向轨道和 hover 内容中，无法快速回答“该位点最重要的证据是什么”。
4. **GO、AlphaGenome、Disease differential expression 的默认视图未突出结论。** GO 等权 label 堆叠；AlphaGenome 默认需要三步选择后才出现图；差异表达的当前蛋白效应值藏在展开项中。
5. **运行方式仍是本地开发栈。** 当前为单 Uvicorn + <code>next dev</code>，无正式反向代理、TLS、依赖锁定、统一 release、缓存和可观测性。所有非 PDB JSON 被强制 <code>no-store</code>。

建议先做四个 P0：**科研发布信息补齐、Site evidence dossier、详情页信息架构与按需取数、正式发布与 release-aware cache**。高级动画和更多图表应排在这些工作之后。

## 1. 当前技术架构

### 1.1 数据究竟分为几层

从“持久化职责”看，当前数据应定义为 **4 个持久化层 + 1 个无状态交付层**。如果从科研内容看，则包含 Core/Annotation、Sequence/Site、Variant、Expression、QTL、Interaction、Disease、Differential expression、Structure、AlphaGenome、Anatomy 等领域；这些是科研主题，不是额外的物理存储层。

~~~mermaid
flowchart TB
    L1["L1 不可变上游事实层<br/>View Parquet / 外部分析结果 / 结构归档"]
    L2["L2 语义与映射契约层<br/>source registry / crosswalk / feature map / bridge"]
    L3["L3 查询 Mart 与摘要索引层<br/>6 个 DuckDB / summary / catalog / manifest"]
    L4["L4 明细与可视化资产层<br/>128 桶 ZSTD Parquet / AlphaGenome tile / PDB.gz"]
    API["无状态只读交付层<br/>FastAPI /api/v1"]
    WEB["展示层<br/>Next.js / React / ECharts / 3Dmol"]
    L1 --> L2 --> L3 --> L4 --> API --> WEB
~~~

### 1.4 前端技术栈

审查时实际安装版本：

- Next.js 16.3.0，App Router；
- React / React DOM 19.2.8；
- TypeScript 7.0.2，strict；
- ECharts 6.1.0，用于 QTL、差异表达和 AlphaGenome；
- 3Dmol 2.5.5，用于结构查看；
- Canvas/SVG 与手写表格、筛选和序列导航；
- CSS variables + 分区样式文件，无现成 UI 框架。

优点是依赖少、科研语义直接体现在页面代码中，ECharts 和 3Dmol 已动态加载。问题是 protein route 整体为 client page，core overview 在 hydration 后才请求，随后大多数区段一起挂载；<code>sequence-explorer.tsx</code> 已达 1,018 行，<code>lib/api.ts</code> 854 行，页面状态、科研解释和网络装配的 locality 下降。

<code>package.json</code> 对 Next/React/TypeScript 使用 <code>latest</code>，虽 lockfile 固定了本机版本，重新解析依赖仍有不可控升级风险；应改为明确版本并由受控升级流程更新。

### 1.5 后端与数据处理技术栈

- Python 3.13.12；
- FastAPI 0.136.0 + Pydantic 2.12.3；
- Uvicorn 0.44.0；
- DuckDB 1.5.3，运行期 read-only；
- NumPy 2.3.5、PyYAML 6.0.3；
- ETL 主要使用 Python、DuckDB SQL 和 Parquet。

接口采用 <code>/api/v1</code>，有 search、protein、sequence/site、variant、QTL、interaction、disease、DE、structure、AlphaGenome、anatomy 等领域路由。PDB 已实现 ETag、Range、Last-Modified 和一年 immutable cache；其他 JSON 则被统一强制 <code>Cache-Control: no-store</code>。

当前各领域通常每请求打开并关闭只读 DuckDB connection。数据规模尚可，但并发下有重复连接开销；应在每 worker 内采用受限连接管理并压测，不能跨线程无保护共享同一个 connection。

### 1.6 当前部署方式

<code>start-local.sh</code> 在 <code>127.0.0.1:8000</code> 启动单 Uvicorn，在 <code>127.0.0.1:3000</code> 启动 <code>next dev --webpack</code>；Next rewrite 将同源 <code>/api/v1/*</code> 转发到 FastAPI。这是合理的本地开发方式，不是公网生产部署。

当前未发现 Python requirements/pyproject/lock、Nginx/Caddy、systemd、Docker、TLS 或 CI 配置。正式上线前至少需要：

- 明确的 Python 和 Node 依赖锁；
- <code>next build && next start</code>；
- 受监管的 FastAPI workers；
- Nginx/Caddy 同源反代、TLS、Brotli/gzip、安全响应头和限流；
- release readiness、结构化日志、指标和回滚；
- 数据目录以只读方式挂载。

### 1.7 审查验证结果

- Backend tests：82 passed；
- ETL tests：17 passed；
- Frontend navigator tests：11 passed；
- TypeScript <code>tsc --noEmit</code>：通过。

本机 warm 单接口多在约 14–102 ms，说明当前首先不需要把 DuckDB 迁移到 PostgreSQL。更直接的问题是：

这些数值是本机审查快照，不应当作公网 SLA；它们用于确定优化顺序。

## 2. catVariant 对标审查

### 2.1 值得借鉴的设计

本次审查浏览了 [catVariant 主页](https://catvariant.com/)、[Analyze](https://catvariant.com/analyze)、[KCNH2 基因页](https://catvariant.com/genes/KCNH2)、[G572S 变异深链](https://catvariant.com/genes/KCNH2/variants/G572S)、[Documentation](https://catvariant.com/documentation) 和 [OpenAPI](https://api.catvariant.com/openapi.json)。其论文为 [Nucleic Acids Research，DOI: 10.1093/nar/gkag518](https://doi.org/10.1093/nar/gkag518)。

catVariant 的核心优势不是“颜色多”，而是研究路径连续：

1. 首页先说明数据库价值、规模、示例和论文，再让用户进入 Analyze 或公开结果。
2. 查询支持 gene/protein/UniProt/FASTA，并先展示匹配蛋白，减少错误身份进入结果页。
3. 基因页顶部用自然语言摘要和覆盖率卡片回答“这是什么、现有什么数据”。
4. 全站导航和结果页二级 sticky 导航分开；滚动时有 active section，移动端收为目录。
5. Universal Search 能在当前基因内检索 residue、HGVS、rsID、疾病、PMID 等，并按实体分组。
6. Variant Catalog 遵循“计数 → evidence chips → 多条件筛选 → 位置索引 → 表格 → 行级详情”的顺序；过滤状态、结果数和 CSV 下载都可见。
7. Sequence、Structure、Catalog 与单 variant 详情形成联动；稳定 URL 支持从基因页深入到单变异证据。
8. Citation、Share、Download、Documentation 在研究路径中反复出现，而不是藏在页脚。
9. 视觉上大面积保持中性，仅用 section icon、数字、badge 和小图标建立定位；标题、说明、控件、图、表的顺序高度一致。

### 2.2 memVar 与 catVariant 的差距

| 维度 | catVariant 的做法 | memVar 当前 | 追赶方案 |
|---|---|---|---|
| 首页定位 | 价值主张、实时规模、示例、论文、CTA | 页面干净但稀疏，且仍写 M3 | 加总览统计、Example EGFR、Browse、Paper/Cite、Release、Download |
| 查询入口 | 多种蛋白输入，并先确认匹配 | 蛋白 search 对 ID/alias 和歧义处理不错，但只有单入口 | 保留 exact-first 优势，扩展 protein 内 universal search |
| 详情总览 | 自然语言摘要 + coverage cards | 先列基本事实，未回答“哪些证据最值得看” | 增加 evidence coverage matrix 和 2–3 句受控摘要 |
| 导航 | 两层 nav、active state、移动目录 | 十个平级链接，无 scrollspy；窄屏横向溢出 | 合并为 5 个研究任务组，桌面目录 + 移动 drawer |
| 高密度浏览 | filter chips 带数量、位置索引、可下载表 | 各领域筛选形式不一致，URL 状态不完整 | 统一 query/filter/count/clear/sort/deep-link 模式 |
| 单位点审计 | variant 深链内纵向证据栈 | Site preview 主要是 variant，其他证据分散 | 建立 canonical Site evidence dossier |
| 引用与下载 | 每页 Share/Citation/Download | 仅部分 PDB 下载；缺数据版本/标准引用 | per-protein/site CSV/JSON，BibTeX/RIS，release/access date |
| 可视化节奏 | 每节“解释—控件—图—明细” | 多处先出现控件或长 label，默认结论弱 | 统一为 takeaway—metrics—visual—details—provenance |
| 科学语义 | 多源证据高度整合 | memVar 更强调来源分离和不可推导共识 | 保留 memVar 的谨慎，这是优势而非差距 |

### 2.3 不应照搬的部分

catVariant 的主观流畅并不等于可以复制其全部实现。本次单次审查观察到部分页面存在很大的 decoded 响应、长 DOM 和大量可聚焦按钮；memVar 不应把“整页先加载完”当成目标。还应避免：

- 复制其账号、任务队列、上传和 Public/Private 流程；memVar 当前是只读论文数据库，不需要扩大产品范围。
- 复制 disease support 或跨源 priority score；memVar 合约明确禁止把来源折叠成伪共识。
- 用自动自然语言把有冲突的多源记录写成确定结论；摘要必须经过 entity、coordinate、source 和 contradiction QC。
- 复制视觉资产、色彩或布局细节；应借鉴信息结构，并保持自己的视觉识别与学术合规。
- 把每个 residue 都做成独立 tab stop；应使用虚拟化和 roving focus，避免键盘用户经过数百个按钮。

## 3. 科研数据库展示评审

### 3.1 当前做得好的部分

- 以 reviewed human membrane protein 和 canonical UniProt accession 为页面身份，搜索结果显示匹配字段并保留歧义。
- 1-based canonical protein coordinate 被持续强调，Variant、Sequence、Structure 间已有联动基础。
- Expression 不把 HPA RNA、MS、IHC、PaxDB 合成一个虚假数值。
- QTL、Interaction、Disease 保留 source/release/evidence grain，不自动生成跨来源共识。
- 分页和有界查询已经用于大明细，运行时不扫描全量 QTL。
- 空状态通常解释“当前发布未发现”而不是把 missing 当成 zero。

### 3.2 需要改进的研究任务路径

科研用户通常按以下问题行动：

~~~mermaid
flowchart LR
    A["找到正确蛋白"] --> B["判断有哪些证据"]
    B --> C["定位关键位点/组织/疾病"]
    C --> D["筛选并比较记录"]
    D --> E["追溯来源与方法"]
    E --> F["下载、引用、分享同一状态"]
~~~

memVar 已覆盖 B–E 的大量数据，但 A、B 的引导以及 F 的闭环不完整。建议：

#### 首页与 Browse

- 首页将 “M3” 改为实际 release 和覆盖域；显示蛋白数、可映射 Variant/QTL/Disease/AlphaGenome 的蛋白数，而不是物理文件总行数。
- 提供 Example EGFR、Browse by gene、membrane class、pathway、tissue、disease evidence availability。
- 新增全站一级入口：Search、Browse、Download、API/Docs、Cite、About。
- 首页的统计卡点击后必须进入已应用该条件的结果集，而不是装饰数字。

#### 搜索

- 保留 exact accession/gene 优先、alias 次之、fuzzy 最后的排序，并继续显示 match reason。
- 在蛋白页增加 universal search：canonical residue、AA change/HGVS、rsID、GO/Reactome、Disease/HPO、tissue、PMID/source record。
- 搜索结果按 Protein / Site / Variant / Disease / Annotation / Publication 分组；每组显示数量和目标章节。
- 筛选、排序、选中 site/contrast/track 写入 URL，刷新、复制链接和浏览器返回后状态不丢失。

#### 结果组织

- protein header 下先放 evidence coverage：哪些领域有数据、数量、最后更新、是否 prediction。
- 页面遵循三层渐进披露：**总览结论 → 可交互摘要 → 分页/下载明细**。
- 表格统一提供：结果数、active filters、clear all、排序、列解释、source/version、CSV/JSON 导出。
- 每条记录保留原生 source ID 和外链；对 ambiguous mapping、conflict、not available 使用不同状态，而非一个灰色空值。

#### 引用与可重复性

新增固定 “Cite this record”：

- 数据库论文引用；
- 当前 <code>release_id</code>、访问日期、protein/site/variant URL；
- BibTeX、RIS 和纯文本复制；
- 数据来源引用和许可；
- 当前筛选结果的 CSV/JSON；
- 面向程序化使用的版本化 OpenAPI 文档。

论文上线前应给每个 source 补 release/version、访问日期和 license。不得用 “not_recorded” 进入正式 release。

## 4. 四个重点展示问题的具体改造

### 4.1 GO：从等权 label 堆叠改为可审计的 annotation 视图

#### 当前问题

当前 GO 只有 Molecular function、Biological process、Cellular component 三个文本数组，所有 term 被渲染为同等视觉权重的 pill。对于长术语或 term 较多的蛋白：

- label 频繁换行，用户先看到形状而不是语义；
- 没有 GO ID、definition、evidence code、reference、source release；
- 无搜索、aspect 筛选、ontology 层级或 ancestor/descendant 关系；
- 所有 term 看似“同等重要”，但页面没有说明这种等权只是展示方式。

当前数据不是 GO enrichment 结果，因此**不应**为了好看而画带 FDR、gene count 或“重要性分数”的气泡图；这些统计在单蛋白 annotation 语境中并不存在。

#### 建议的信息结构

1. 顶部放 3 张 aspect summary：MF / BP / CC，各显示 term 数和代表性 term。
2. 代表性 term 不是“生物学评分”，而是由公开、确定性的导航规则选出，例如：优先保留最具体的非祖先 term，再按 ontology depth 和 label 排序；规则写入方法页。
3. “View all annotations” 打开可搜索列表或 drawer：
   - term label；
   - GO ID 与 QuickGO/AmiGO 外链；
   - aspect；
   - evidence code；
   - negation；
   - reference/PMID；
   - source/release。
4. 支持按 aspect、evidence class、with/without reference、negated 过滤；长 label 最多显示两行，展开后看 definition。
5. 若要画图，优先画小型 ontology tree 或 ancestor breadcrumb；不要发明 enrichment 数值。

这需要把当前 <code>go_summary</code> 扩展为 <code>go_evidence</code> mart。现有设计文档已经预留 GO ID、aspect、evidence 和 reference，属于完成既定契约，而非新增不受控功能。

### 4.2 Site：建立真正的纵向 Site evidence dossier

#### 当前问题

Sequence explorer 的横向全长轨道是很好的定位工具，但不适合承载全部解释。审查 EGFR 的 site 状态发现：

- JSD 只有细线与 0–1 范围，没有可持续查看的精确值、occupancy、Neff 或 confidence；
- Stability 的中位数/范围/替换细节主要在 hover 卡中，极端值还会被固定显示范围裁剪；
- covalent pair 点击后只选中一个端点，partner、type、description 和 evidence 没有纵向呈现；
- Site preview 主要列 Variant，未统一呈现 topology、Pfam、functional、PTM、JSD、stability 与 covalent；
- 信息依赖 hover，对触屏和键盘用户不友好。

#### 推荐布局

桌面端在 sequence 右侧使用约 360–420px sticky drawer；移动端使用 bottom sheet。横向轨道负责“找位置”，纵向面板负责“读证据”。

~~~text
Selected canonical site · Residue 858                    [Copy link] [×]
Identity
  Residue / canonical position / sequence version / selected range

Key signals
  Conservation JSD        0.xxx       confidence · occupancy · Neff
  Stability ΔΔG median   +x.xx kcal/mol   IQR / min–max / n substitutions
  Covalent link           858 ↔ partner   type · description

Context
  Topology / Pfam / functional interval / PTM overlapping this site

Stability substitutions
  Mutation      ΔΔG       direction       model/version

Variants
  total / ClinVar P/LP presence / source badges / bounded rows

Provenance and interpretation limits
  source · release · coordinate basis · what this does not imply
~~~

#### 数据与交互实现

新增强类型只读接口：

<code>GET /api/v1/proteins/{acc}/sites/{position}/summary</code>

返回：

- identity：accession、sequence version、1-based position、reference residue；
- conservation：JSD、entropy、WT frequency、gap、occupancy、Neff、alignment scope、confidence；
- overlaps：topology、Pfam、functional interval、PTM；
- stability：min/q25/median/q75/max、替换数、全部 substitutions、model/release；
- covalent：pair ID、两个端点、type、description、evidence；
- variants：总数、ClinVar P/LP presence、bounded preview、source counts；
- provenance 与 interpretation note。

具体交互：

- site、range、pair ID 写入 URL；刷新和分享后可恢复。
- 任一轨道、residue grid、variant row、structure residue 点击都更新同一个 selected-site state。
- JSD 可显示“蛋白内 percentile”作为导航辅助，但必须离线计算、清楚标为 within-protein rank，不能解释为跨蛋白功能评分。
- Stability 显示零线、IQR、min–max；超过可见量程时给越界箭头，或在选中后自适应 y 轴。
- covalent 在序列上采用弧线/连接线，面板中始终同时显示两个端点；点击 partner 可跳转且保留返回路径。
- drawer 内信息可聚焦、可滚动，不依赖 <code>pointer-events: none</code> 的 hover 卡。

### 4.3 AlphaGenome：从“轨道配置器”改为“先看概览，再做比较”

#### 当前问题

当前 summary 只显示 mapped gene、display-ready 和 local tracks 数；展开后必须完成 modality → biosample → track 三步才出现图。492 local tracks 是库存信息，不等同于用户要回答的问题。页面缺少 gene/transcript/exon 锚点，多个 contact map 的独立色标也不利于横向比较。

#### 推荐的两级视图

**一级：At a glance**

- 映射状态：exact / ambiguous / no Ensembl / no prediction 分开显示；
- gene、Ensembl ID、GRCh38 locus、strand、1 Mb model window；
- 当前 gene 的 modality coverage matrix，而不是全 catalog 总数；
- gene model + exon/transcript 轨道；
- 2–4 个由配置文件声明的 Overview preset small multiples；
- 一句话限制：reference-sequence prediction，不是实验测量、致病性结论或 variant-effect。

Overview preset 必须是确定性、可解释的展示配置，例如由 <code>alphagenome_presets.yaml</code> 声明 assay、biosample 和排序；它表示“默认示例”，不暗示该 tissue 最重要。若无合适 preset，则只显示 coverage matrix 并引导选择，不自动声称生物学显著性。

**二级：Advanced comparison**

- 可搜索 biosample picker，按 ontology/tissue 分组；
- 共享 genomic axis、brush、crosshair 和 URL state；
- signal 使用上下排列的 small multiples，保留各自单位和 y-scale；
- contact map 可切换 shared color scale，且始终显示数值范围；
- junction 过密时先聚合，点击后显示可 pin 的区间和值；
- 最多比较 3–5 条轨道，并明确为何达到上限；
- 提供当前视图数据 CSV/JSON、图 SVG/PNG、source/model/version。

### 4.4 Disease differential expression：先显示当前蛋白的方向和量级

#### 当前问题

当前 summary 只返回 <code>is_significant_with_effect = TRUE</code> 的 contrast；“被检测但不显著”完全不出现。用户必须先展开 dataset、再选择 contrast，当前蛋白的 mean expression、log2FC 和 FDR 还藏在第二层 details 中。这会把“没有资格进入列表”误读成“没有被检测”。

Volcano 的 current protein 星形是正确基础，但 27,742 点的单响应可达 4.22 MB 原始 JSON；结论和性能都还有改进空间。

#### 推荐结构

1. 顶部先回答：
   - 当前蛋白被多少 contrast 检测；
   - 多少为 significant with effect；
   - up / down / not significant 数；
   - mapping 是否 exact 或 multiple gene rows。
2. dataset/contrast 行的第一视觉层直接显示：
   - disease、tissue；
   - Up / Down / Not significant；
   - log2FC；
   - FDR；
   - mean expression；
   - case/control n 与 paired 状态。
3. 默认排序规则公开：significant first → FDR → |log2FC| → contrast ID。可默认展开第一项，但要标明排序规则，不能写成“最重要疾病”。
4. 添加有零线的水平 effect strip；只有 upstream 真实提供 SE/CI 时才显示 uncertainty，不能由 FDR 反推。
5. Volcano 保留所有 target 和 membrane genes；背景改为确定性密度/分层采样。提供“Load full plot”与全量下载。
6. current protein 使用持久文字 callout，并在图旁固定显示 log2FC/FDR/direction，而不只依赖 hover。
7. dataset、contrast、selected gene 写入 URL。
8. 空状态明确区分：not tested、unmappable、tested but not significant、qualifying but data unavailable。

### 4.5 全站文字表达模板

当前许多文字在解释“控件如何操作”，但没有先说“数据告诉用户什么”。每个 section 统一为：

1. **Takeaway：** 一句当前蛋白结论；
2. **What is measured：** 数据/模型测量的对象；
3. **How to read：** 方向、单位、阈值；
4. **Limitations：** 不能推导什么；
5. **Source：** 数据库、release、原生记录。

示例：

- Stability：先写 “Predicted stability changes are available at N canonical sites”，再说明负值/正值和 ThermoMPNN 非临床证据。
- AlphaGenome：先写 “Reference-sequence regulatory predictions are available for ENSG…”，再进入轨道选择。
- DE：先写 “EGFR is upregulated in X of Y qualifying contrasts”，随后给 disease/tissue 和效应；不要先写 “Select a dataset, then a contrast”。
- Disease：先写各来源覆盖数和是否存在 conflict，再展开来源卡；不得写跨来源共识。

### 5.2 字体和字号

- 使用 <code>next/font/local</code> 固定 Inter Variable 或 Source Sans 3，避免当前只声明 Inter、实际回退到系统字体。
- ID、coordinate、variant、数值列使用 IBM Plex Mono 或系统 monospace。
- 正文 16px/1.55；表格与控件 14px；辅助 metadata 不低于 12.5–13px；section title 28–32px。
- 使用 <code>font-variant-numeric: tabular-nums</code> 对齐 coordinate、log2FC、FDR、ΔΔG。
- 只对真正结论、方向、数值和可操作入口使用粗体；不要让每个 label 都是 badge/uppercase/bold。

### 5.3 配色

当前 11 色 pastel palette 可保留为数据色板，但要把三种职责拆开：

- **品牌/导航色：** 1 个主色；
- **科研语义色：** up、down、neutral；stabilizing、destabilizing；prediction、observed；
- **状态色：** success、warning、conflict、missing。

颜色不能单独编码含义，必须同时有文字/形状。建议：

- up / destabilizing：coral + upward symbol；
- down / stabilizing：blue/teal + downward symbol；
- neutral/not significant：slate；
- prediction：浅黄边框 + “Predicted” 文本；
- conflict：红色边框 + conflict icon；
- missing：中性虚线，不使用零值颜色。

所有正文与小字达到 WCAG AA。大量白底卡片保持中性，section 色只用于细窄定位条、图标或 active state，不要让每个卡片都使用不同背景色。

### 5.4 高信息量页面的降负担原则

- 先给数量和覆盖，再出现筛选；
- active filters 固定可见，一键清除；
- long-tail 内容折叠，但当前蛋白结论不折叠；
- legend 靠近图且可交互；重复 legend 合并；
- 表格 sticky header，字段 tooltip，默认列不超过 6–8 个，其余在 row detail；
- 列表/网格使用分页或虚拟化，不把数百记录全部放入 DOM；
- 图表附文本摘要和可访问数据表；
- 图标使用项目自有 SVG 或明确许可素材，避免直接复制 catVariant 视觉资产。

## 6. 数据工程、前端工程与运维优化

### 6.1 发布一致性和可重建性

当前各构建器可分别替换 M2、M3、M4、ThermoMPNN、AlphaGenome 等目录，线上进程可能短暂看到“新 summary + 旧 detail”。改为整版发布：

~~~text
website/data/releases/<release_id>/
  memvar_core.duckdb
  memvar_m2.duckdb
  memvar_m3.duckdb
  memvar_m4.duckdb
  differential_expression/
  alphagenome/
  sequence/
  variant/
  ...
  release_metadata.json
~~~

在 staging 目录完成 ETL、schema contract、row-count invariant 和 smoke test，再让进程通过 <code>MEMVAR_GENERATED_ROOT</code> 指向新版本并重启。AlphaGenome 路径安全检查当前拒绝符号链接，因此不要直接假设 <code>current</code> symlink 可用；可用受控配置/环境变量切换完整目录。

<code>release_metadata.json</code> 至少包含：

- release_id、schema_version、built_at_utc；
- builder source revision；
- 每个 source 的 release/access date；
- build scope、表/文件行数、bucket count；
- semantic contract version；
- serving-ready 与 rebuild-ready 状态。

它不是质量总分，也不需要扩张为全量 hash inventory。AlphaGenome 原始路径未挂载时，应明确 “serving ready, rebuild not ready”。

### 6.2 缓存与传输

取消 JSON 全局 <code>no-store</code>，缓存键必须包含 release：

- summary/catalog：<code>public, max-age=300, stale-while-revalidate</code>；
- release 固定的 exact tile/detail：<code>public, max-age=31536000, immutable</code>；
- ETag：release_id + canonical request key；
- 客户端使用 SWR/React Query 或轻量等价层做 request dedup、缓存和错误重试；
- Nginx/Caddy 开启 Brotli/gzip。

Sequence overview、contact map 和 DE volcano 的压缩收益明显。对缓存的验收必须包含 304/HIT、release 切换后不串版，以及 PDB Range 请求不回退。

### 6.3 首屏和渐进加载

- protein header、identity 和 evidence availability 改为 Server Component/SSR；
- 每个 section 只在进入视口、用户展开或导航跳转时加载；
- Disease 先用一个 summary 返回五个来源的 count/badge，再展开取 source detail；
- Structure 与 Sequence 共享已加载的 sequence density，消除 bins=100/400 重复请求；
- ECharts 按具体 chart 子模块引入，避免一个早挂载的 QTL summary 提前加载整包；
- 3Dmol、AlphaGenome contact map 和全量 volcano 始终延迟。

### 6.4 大响应和查询

#### Differential expression

- overview 只发 target、全部 membrane points、显著/极值点和确定性背景样本或密度网格；
- 全量点作为明确的“完整图/下载”请求；
- 继续使用 Canvas/WebGL，不能退回大 SVG DOM；
- 对 contrast 响应增加压缩、ETag 和 size budget。

#### AlphaGenome

AlphaGenome 占 generated 的 93.8%，是存储专项。保留 catalog-first 和 gene/tile 精确寻址。当前常见 track tile 只有一个大 row group，按 track_id/level_bins 读取时会产生读放大；应做小规模 A/B：

- 仍保持每 gene/tile 一个文件，避免数百万小文件；
- 行按 track_id、level_bins 排序；
- row group 对齐单 track 或小 modality block；
- 比较冷缓存延迟、读取字节、metadata 开销后再决定。

增加严格字节上限的热点 LRU，key 包含 release、gene、tile、track/modality、bins、window。catalog 和高频 summary 放本地 NVMe；若 tile 放对象存储，必须先验证 Range read 和延迟，不能直接把当前文件访问模式搬到网络盘。

#### DuckDB / Parquet

- 通过 FastAPI lifespan 管理每 worker 的受限只读连接或线程本地 connection；并发压测后决定数量。
- QTL/Interaction 无筛选时直接使用 summary count；常用 filter count 和稳定 sort key 在 ETL 预生成。
- ART index 只对真实慢查询 A/B 测试，不要给所有列机械建索引。
- <code>source_registry.yaml</code> 启动时校验并缓存。
- Structure manifest 启动时加载索引或并入 catalog DuckDB。

### 6.5 生产部署

推荐最小生产拓扑：

~~~mermaid
flowchart LR
    U["Browser"] --> P["Nginx/Caddy<br/>TLS · Brotli · cache · rate limit"]
    P --> N["Next production<br/>SSR + static assets"]
    P --> F["FastAPI workers<br/>read-only"]
    F --> C["DuckDB catalogs<br/>local NVMe"]
    F --> A["immutable Parquet/PDB/tiles<br/>read-only release"]
~~~

具体要求：

- systemd 或容器 supervisor 管理进程，禁止用 dev server；
- backend 只绑定 loopback/Unix socket；
- CSP、HSTS、X-Content-Type-Options、Referrer-Policy；
- 对 signals、volcano、PDB、批量下载设置参数上限与 rate limit；
- <code>/live</code> 只检查进程；<code>/ready</code> 校验 6 个 DuckDB、manifest、release 一致性和抽样 bucket/tile；
- 结构化 access/error log，request ID；
- 指标至少包括 endpoint p50/p95、query time、response bytes、cache hit ratio、error rate；
- rollback 保留上一完整 release。

### 6.6 依赖、测试和 CI

- 将 Node 依赖从 <code>latest</code> 改为明确版本，CI 使用 <code>npm ci</code>；
- 建立 <code>pyproject.toml</code> + lock，固定 Python 3.13 和二进制兼容依赖；
- package scripts 增加 lint、typecheck、unit、e2e、build；
- CI 顺序：schema/ETL unit → backend unit → frontend unit/typecheck → production build → Playwright smoke；
- E2E 至少覆盖 P00533：
  - search → protein；
  - section nav 与 mobile drawer；
  - select site → JSD/ΔΔG/covalent/variant drawer；
  - select DE contrast → target callout；
  - AlphaGenome preset → advanced track；
  - copy citation / download；
- 加 axe accessibility、390px/768px/1440px responsive snapshot 和视觉回归；
- release smoke 使用 production build 和隔离 distDir，避免现有 Next dev lock 干扰。

### 6.7 SEO 与长期科研发现

- protein route 的 title、description、canonical URL 在服务端生成；
- 输出 DataCatalog/Dataset 或 BioChemEntity JSON-LD；
- XML sitemap 收录稳定 protein 页面，不收录临时筛选组合；
- 页面 HTML 中包含 protein name、accession、gene、release、citation，不能只输出 loading shell；
- DOI、论文、license、维护机构、联系方式和数据更新政策放入 About/Cite。

## 7. 架构深化建议

以下建议使用 module depth、leverage 和 locality 作为评审标准：外部 Interface 要小而稳定，内部 Implementation 可以承载复杂性；不是为了把大文件机械拆成更多 shallow module。

| 候选 | 当前状态 | 建议的深 Module / Interface | Leverage 与 locality | 判断 |
|---|---|---|---|---|
| Selected Site Evidence | JSD、feature、PTM、stability、covalent、variant 的装载和解释散在 1,018 行 Sequence explorer 与多个接口；SitePreview 仍是弱类型 | <code>SelectedSiteEvidence</code> Interface 只暴露 identity、signals、overlaps、variants、provenance；内部 Implementation 负责跨表读取、科学解释和 UI view model | 一个 Interface 同时服务 sequence、structure、variant deep-link 和 mobile drawer；显著提高 leverage，并把 site 规则放回一个 locality | **Strong** |

- 把每个小卡片拆成只传 props 的 pass-through file，不增加 depth；
- 造一个“统一 evidence score/query”抽象，掩盖 QTL、Interaction、Disease 的来源语义。

### 8.1 建议的可量化验收指标

**科研可信度**

- 100% 页面显示 release、reference coordinate、source/version、citation；
- GO detail 的 100% 行具有 GO ID；evidence/reference 缺失时显式标注；
- DE summary 同时报告 tested 与 qualifying；
- prediction、observed、curated evidence 在 UI 中有一致标识。

**可用性**

- 用户从搜索到打开某 residue 的完整证据不超过 3 次主要操作；
- 5 名目标科研用户完成“找到 EGFR 某 site 的 JSD、ΔΔG 和 covalent partner”成功率 ≥ 80%；
- active section、filter、site、contrast、AlphaGenome track 可通过 URL 恢复；
- 390px、768px、1440px 均无页面级横向溢出。

**性能**

- protein header 和 evidence availability 出现在首个服务端 HTML；
- warm site-summary p95 目标 < 300 ms，需注明硬件与并发；
- DE overview gzip < 500 KB；全量数据走显式下载；
- repeat navigation 命中 client/server cache，不重复下载 immutable payload；
- production Lighthouse Performance 建议 ≥ 85，Accessibility ≥ 95。

**运维**

- 一个 release 的所有 mart/manifest 具有相同 release_id；
- readiness 能阻止混合 release 上线；
- 结构化日志可定位最慢 endpoint 和最大响应；
- 回滚完整 release 的演练时间 < 10 分钟。

## 9. 优化时必须保留的科学边界

1. ThermoMPNN ΔΔG 不是功能或致病性评分；负值预测稳定、正值预测去稳定，必须给单位、model/version。
2. HPA RNA、MS、IHC、PaxDB 不合成单一 expression 值；missing 不补零。
3. QTL 始终保留 source、release、genome build 和 source-specific semantics。
4. Interaction 的 evidence record 数与 native interaction ID 数不能混为一个总数。
5. Disease 来源不可自动投票或生成“共识结论”；quarantine 数据不得进入公开聚合。
6. AlphaGenome 是 reference-sequence prediction，不能冒充实验测量、临床证据或 variant-effect。
7. GO annotation 不是 enrichment；没有 FDR 时不得画伪显著性图。
8. 为性能做抽样时，必须保留 target、阈值、计数和下载全量的路径，并公开抽样规则。
9. 运行时继续禁止扫描完整 QTL/AlphaGenome 原始数据，也不引入在线模型推理。

## 11. 最终建议

memVar 不需要成为 catVariant 的复制品。它最有价值的差异是：围绕膜蛋白，把 sequence、site、structure、expression、QTL、interaction、disease、DE 和 AlphaGenome 放在同一 canonical coordinate 与严格来源语义下。下一步应把这种数据优势变成清楚的研究路径：

**先回答“有什么、哪一项最值得看”，再让用户定位、比较、审计和引用。**

最先落地的界面应是 Site evidence dossier，因为它能同时解决用户指出的 JSD、Stability ΔΔG、covalent bond、文字层级和跨视图联动问题；最先落地的工程工作应是统一 release + production cache，因为它决定论文数据库能否被稳定引用、重复访问和安全更新。
